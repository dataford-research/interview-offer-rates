A Two-Week PostgreSQL Study Plan for SQL Interviews

By Amney Mounir

SQL shows up in almost every data interview I hear about, from data analyst and product analyst loops to data engineering and data science. The questions are rarely exotic. Most of them test whether you can turn a business question into a correct query, and whether you understand what each clause does to your rows.

Dataford's PostgreSQL Mastery Cheat Sheet covers the syntax from basic SELECT statements to window functions and recursive queries, with a PDF version you can keep open while you practice. Below is how I would turn that reference into a two-week study plan.

Week one: the fundamentals interviewers check first

Start with the building blocks and say out loud what each one does. Interviewers notice when a candidate writes a query that runs but cannot explain why it works.

  • Filtering with WHERE, BETWEEN and IS NULL. A comparison with NULL using = returns unknown, so you need IS NULL or IS NOT NULL. This comes up in interviews all the time.
  • Aggregates like COUNT, SUM, AVG, MIN and MAX. COUNT(*) counts every row while COUNT(column) skips NULLs, and AVG divides by the number of non-NULL values.
  • GROUP BY and HAVING. Every column in SELECT must be grouped or aggregated. WHERE filters rows before aggregation and HAVING filters groups after it.
  • Joins. Practice INNER, LEFT and FULL OUTER joins until you can predict the row count before you run the query. A LEFT JOIN with a NULL check is the standard way to find records with no match.

For each topic, write three queries against small tables you build yourself, such as employees, departments and orders. Then change one condition and predict the new output before you run it. That habit catches most of the mistakes people make under time pressure.

Week two: the patterns that show up in later rounds

Once the basics feel automatic, move to the topics that separate strong candidates.

  • Window functions. RANK() OVER (PARTITION BY ...) for top N per group, SUM() OVER (ORDER BY ...) for running totals, and LAG() for day-over-day or month-over-month change.
  • Subqueries and CTEs. Solve the same problem once with a subquery in FROM and once with a CTE, and notice which version is easier to read out loud.
  • CASE and COALESCE for bucketing users and filling default values, which shows up often in product analytics questions.
  • Date logic with EXTRACT, INTERVAL and age(). Retention and cohort questions depend on getting dates right.
  • Recursive CTEs for hierarchies like org charts. These are less common, but they do appear in heavier data engineering loops.

Practice on real interview questions

A cheat sheet tells you what the syntax is. Real interview questions show you how companies phrase their problems. Dataford's interview question bank has 20k+ real questions tagged by company and role, with step-by-step solutions. Pick the company you are targeting and work through its SQL questions from easiest to hardest.

Give yourself a fixed amount of time per problem and talk through your approach before you type. That is what the live round will feel like, and it is much easier to practice the talking at home than to learn it on the call.

How to talk through a query in the interview

  1. Restate the question and confirm the grain of the output, for example one row per user per day.
  2. Name the tables you need and the keys you will join on.
  3. Write the query in small steps and check intermediate results if the tool lets you run code.
  4. Call out edge cases: NULLs, duplicate rows, ties in a ranking, and users with no activity at all.
  5. Say how you would sanity-check the answer, such as comparing a total against a simple COUNT.

Most SQL mistakes I see in interviews come from skipping the first step. Once you lock the output grain, the joins and aggregations become much easier to get right.

Bookmark the cheat sheet, do a few company questions each day, and you will walk into the SQL round with a plan.
